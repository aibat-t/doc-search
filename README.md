# doc-search

Практика уроков **2.2.2 «Векторные базы»**, **2.2.3 «Индексация документов»** и **2.2.4 «Качество поиска»**:
документы загружаются через API, индексируются воркером через Kafka в pgvector,
а поиск (векторный, полнотекстовый, гибридный, с reranking) возвращает куски документов
с источником, разделом и страницей.

```
POST /documents ──► storage/ + documents (status=queued) ──► Kafka: documents.queued
                                                               │ key = document_id
                                                               ▼
                                  doc-worker: парсинг → чанкинг → эмбеддинги
                                                               │ одна транзакция:
                                                               ▼ DELETE старых + INSERT новых
GET /search ◄──── HNSW (vector_cosine_ops) ◄──────────── chunks (pgvector + tsvector)
```

Поиск (урок 2.2.4):

```
вопрос ─┬─► эмбеддинг ─► HNSW  ─► top-50 ─┐
        └─► tsquery (ИЛИ) ─► GIN ─► top-50 ─┴─► RRF ─► top-50 ─► cross-encoder ─► top-5
            vector      keyword          hybrid                hybrid_rerank
```

## Запуск

```powershell
docker compose up -d          # Postgres + pgvector, Kafka
uv sync
uv run pytest

# в двух терминалах:
uv run doc-worker
uv run doc-api                # http://127.0.0.1:8000/docs
```

Загрузить примеры (или свои PDF/DOCX/HTML/MD/TXT):

```powershell
curl.exe -F "file=@samples/card-rules.md" http://127.0.0.1:8000/documents
curl.exe -F "file=@samples/tariffs.html" http://127.0.0.1:8000/documents
curl.exe "http://127.0.0.1:8000/documents"
curl.exe "http://127.0.0.1:8000/search?q=потерял карту что делать"
curl.exe "http://127.0.0.1:8000/search?q=сколько стоит перевод в другой банк&source=tariffs.html"
curl.exe -F "file=@samples/zakon.pdf" http://127.0.0.1:8000/documents
curl.exe "http://127.0.0.1:8000/search?q=статья 36-1&mode=vector"
curl.exe "http://127.0.0.1:8000/search?q=статья 36-1&mode=keyword"
curl.exe "http://127.0.0.1:8000/search?q=статья 36-1&mode=hybrid_rerank"
```

Режимы `mode`: `vector`, `keyword`, `hybrid` (по умолчанию), `hybrid_rerank`.
Поле `score` в ответе у каждого режима своё (косинус, ts_rank_cd, RRF, оценка reranker'а) — между режимами его не сравнивают.
Первый запуск `doc-api` скачает reranker `bge-reranker-v2-m3` (~2,3 ГБ).

Сравнение режимов (урок 2.2.4) — нужны проиндексированные три файла из `samples/`:

```powershell
uv run doc-eval                 # 20 вопросов × 4 режима, отчёт в eval/last_run.md
uv run doc-eval --verbose       # плюс место правильного ответа по каждому вопросу
uv run doc-eval --modes vector keyword hybrid   # без reranker'а
```

Замеры pgvector (урок 2.2.2):

```powershell
uv run doc-bench
uv run doc-bench --n 50000 --ef 10 40 100 400
```

## Структура

```
src/doc_search/
  config.py      настройки (DOC_*), см. .env.example
  schema.sql     таблицы documents и chunks, HNSW-индекс
  db.py          создание схемы, пул соединений
  parsing.py     PDF / HTML / DOCX / MD / TXT → блоки с разделом и страницей
  chunking.py    блоки → чанки с перекрытием и заголовком
  embedder.py    текст → вектор, счётчик токенов
  repository.py  все SQL-запросы, включая полнотекстовый поиск
  ranking.py     RRF — слияние нескольких выдач по местам
  reranker.py    cross-encoder
  search.py      четыре режима поиска за одним методом
  eval.py        doc-eval: recall@5, MRR, latency по режимам
  messaging.py   Kafka: топики, продюсер, консьюмер
  indexer.py     индексация одного документа (идемпотентная)
  worker.py      цикл чтения Kafka
  api.py         FastAPI
  bench.py       перебор против HNSW: latency и recall
tests/           чанкинг, парсеры, RRF, метрики eval (без БД и Kafka)
eval/            questions.jsonl — вопросы с правильным «файл + раздел»; last_run.md — последний отчёт
samples/         учебные документы
```

## Что проверить руками

- [ ] Загрузить тот же файл ещё раз → ответ `unchanged`, воркер ничего не делает.
- [ ] Изменить файл и загрузить с тем же именем → чанки заменились, `chunk_count` обновился.
- [ ] Остановить воркер, загрузить файл, запустить воркер → документ проиндексируется из очереди.
- [ ] Загрузить скан PDF без текста → статус `failed`, причина в `error`, воркер жив, сообщение в `documents.dlq`.
- [ ] Поиск с `source=...` возвращает k результатов, а не меньше.

## Результаты замеров

| Вариант | среднее, мс | p95, мс | recall@10 |
|---|---|---|---|
| без индекса | 23.43 | 26.03 | 100% |
| HNSW, ef_search=10 | 0.61 | 0.77 | 98.5% |
| HNSW, ef_search=40 | 0.75 | 0.95 | 100% |
| HNSW, ef_search=100 | 0.94 | 1.22 | 100% |
| HNSW, ef_search=200 | 1.57 | 1.88 | 100% |

10 000 векторов × 768, CPU. Индекс строится 2,3 с и занимает 39 МБ.

## Выводы (2.2.2)

- HNSW быстрее перебора в ~30 раз уже на 10 000 векторов, и разрыв растёт с объёмом: перебор линейный, HNSW — примерно логарифмический.
- ef_search=40 (значение по умолчанию) даёт 100% recall@10 за 0,75 мс. ef_search=10 быстрее всего на 0,14 мс, но теряет 1,5% recall — экономить там не на чем.
- Данные синтетические (кластеры). На настоящих эмбеддингах recall при малом ef_search может быть ниже — проверять на своих данных.
- В реальном поиске сам запрос к базе — около 1 мс из 36 мс режима vector. Остальное — эмбеддинг вопроса моделью на CPU. Ускорять в первую очередь нужно модель, а не базу.

## Качество поиска (2.2.4)

20 вопросов: 14 перефразировок (`semantic`) и 6 с точными терминами (`exact`: номера статей, SWIFT, IMEI, телефон 7711).
Скопируйте сюда таблицу из `eval/last_run.md`.

| Режим | recall@5 | MRR | recall@5 (exact) | recall@5 (semantic) | среднее, мс | p95, мс |
|---|---|---|---|---|---|---|
| vector | 90% | 0.81 | 67% | 100% | 36 | 40 |
| keyword | 75% | 0.62 | 83% | 71% | 2 | 3 |
| hybrid | 95% | 0.82 | 100% | 93% | 36 | 40 |
| hybrid_rerank | 100% | 0.97 | 100% | 100% | 27 515 | 31 526 |

CPU, reranker `bge-reranker-v2-m3`, 50 кандидатов. Подробно по вопросам — `eval/last_run.md`.

Выводы:

- **Векторы и слова ошибаются на разных вопросах.** vector не нашёл «7711» и «статья 36-1» (вернул 36-2 и 41-1: для эмбеддинга номера почти одинаковы). keyword провалил 5 перефразировок, где у вопроса и документа нет общих слов («спор по покупке» ↔ «претензия по операции»).
- **hybrid закрыл все exact-вопросы (67% → 100%)**, но MRR почти не вырос (0.81 → 0.82): на трёх вопросах шум от keyword сдвинул правильный ответ векторов с 1-го места на 2–4-е. Вопрос про охранные зоны hybrid потерял совсем: vector держал его на 5-м месте, keyword не нашёл, и RRF вытеснил его чанками, которые нашлись обоими поисками.
- **«статья 36-1» — показательный случай.** Ни vector, ни keyword не дали её в top-5, а hybrid поднял на 4-е место: в обоих списках она была ниже пятого места, но в обоих, и RRF это сложил. Keyword промахнулся, потому что Postgres режет «36-1» на `36` и `-1` (дефис читается как минус), а `-1` встречается в любом «1-1», «41-1». Это лечится нормализацией номеров при индексации.
- **reranking дал максимум качества (MRR 0.97), но 27 с на запрос** — 99,9% всего времени. На CPU с моделью 568M параметров и 50 кандидатами это неприменимо для онлайн-поиска.
- **В прод сейчас взял бы hybrid** (95%, 36 мс). Reranker — только на GPU или с моделью полегче и 20 кандидатами, после замера, сколько recall при этом теряется.
- **Оговорка:** 20 вопросов — это 5 п.п. на вопрос, разница 90% и 95% — один вопрос. Вопросы писались с оглядкой на документы. Для выводов «в прод» набор нужно расширить реальными запросами пользователей.
